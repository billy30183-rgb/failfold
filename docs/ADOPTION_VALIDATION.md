# Validate usefulness before making adoption claims

The delivery contains no users, downloads, stars, maintainer testimonials or human time-savings measurements. A public release and live demo alone would not establish those facts.

Start with consenting maintainers who already inspect repeated JUnit failures. Let them use their own reports locally; do not ask them to upload private logs. Offer a small synthetic public example for reproducibility. Ask whether the reading list helped, which raw evidence they checked and whether matching or splitting was misleading.

For a time study, define the same concrete task for both workflows: identify distinct reported failure signatures and list those absent from a specified baseline. Record completed task accuracy and elapsed time separately. Counterbalance task order or use matched reports to reduce learning effects. Disclose participant count, report selection, machine, normalization mode, rejected inputs and limitations. Do not label different signals as root causes.

Publish only permission-cleared aggregate observations and minimal synthetic regression fixtures. Separate one-time feedback from recurring use. Use issues, actual fixes and releases as maintenance evidence. Do not seed fake issues, backdate commits, purchase stars, trade approval claims or state targets as achieved metrics.

Use the maintainer feedback to choose the next small change. More integrations are not inherently better than fixing one proven compatibility or evidence-retention problem. The application should link real evidence, not projected adoption.

An example internal readiness milestone is several independent maintainers completing the task and at least one feedback-driven fix. This is a suggested product-validation milestone, **not an OpenAI eligibility threshold or a guarantee of selection**.
